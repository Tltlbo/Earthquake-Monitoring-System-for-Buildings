## 1. 현재 구현과 근거

현재는 기둥 한 개를 촬영해 기울임에 따른 상태를 감지한다. YOLO로 이미지에 박스를 표시할 때 시간이 오래 걸려 Keras 모델을 선택했다는 배경은 개발자의 설명에 근거한다. 현재 저장소에는 YOLO 비교 코드와 성능 로그가 없어 당시 지연의 정확한 병목과 개선량은 확인할 수 없다.

아래 파일을 검토했다. 이 문서는 코드에서 확인한 사실과 향후 제안을 구분한다.

## 2. Keras 모델을 선택한 이유

초기 YOLO 방식에서는 검출 박스를 표시하기까지 시간이 오래 걸렸다. 현재 목적은 여러 객체의 위치를 찾는 것이 아니라 고정된 기둥 하나의 상태를 감지하는 것이므로, 이미지 분류를 수행하는 Keras 모델을 선택했다.

현재 코드는 다음 순서로 동작한다.

1. `load_model(..., compile=False)`로 모델을 읽고 `VideoCapture(0)`으로 프레임을 얻는다.
2. BGR을 RGB로 변환하고 `ImageOps.fit`으로 중앙 크롭·224×224 리사이즈를 수행한다.
3. 픽셀을 `[-1, 1]`로 정규화해 `(1, 224, 224, 3)` 입력으로 추론한다.
4. 최고 점수의 클래스를 선택하고 같은 클래스가 5프레임 연속 나오면 확정한다.
5. `WARNING / CAUTION / SAFETY` 문자열을 TCP로 전송한다.

즉, **현재 출력은 각도 수치나 객체 좌표가 아니라 3개 상태 분류**다. 중앙 크롭은 기둥을 자동 검출해 자르는 ROI 처리도 아니다. 코드에는 Teachable Machine 전처리라는 설명이 있지만 학습 데이터와 과정은 확인되지 않았다.

Keras는 모델 구축·학습 프레임워크이고 YOLO는 객체 검출 모델 계열이다. “Keras가 항상 더 빠르다”보다 “단일 기둥 상태 분류에 맞춰 검출·박스 표시 경로를 단순화했다”는 설명이 적절하다. 현재는 영상 표시도 비활성화되어 있어 비교 시 표시 유무의 영향까지 분리해야 한다.

### YOLO 표시 지연의 재검증

늦게 나타나는 박스의 원인은 촬영 버퍼·전처리·추론·후처리·그리기·화면 출력 중 어느 단계든 될 수 있다. 버전에 따라 NMS도 후처리에 포함될 수 있다. 결과 표시 지연만으로 그리기 함수가 병목이라고 단정하지 않는다. Ultralytics도 전처리·추론·후처리 시간을 구분한다. [공식 예측 문서](https://docs.ultralytics.com/modes/predict)

동일 보드·영상·표시 조건에서 단계별 시간과 종단 지연을 비교한다. 워밍업을 구분하고 GPU 작업 완료를 반영해 측정한다. 평균 FPS 외에 촬영부터 수신까지의 p50/p95/p99와 프레임 큐 적체를 확인한다.

## 3. 단일 기둥 감지의 장단점과 개선

### 장점

- 224×224 입력과 3개 클래스로 현재 요구사항을 단순하게 표현한다. 객체 좌표와 박스 표시가 필요하지 않다.
- 상태 문자열만 보내므로 영상을 보내는 방식보다 전송량이 작다. 실제 절감량은 측정하지 않았다.
- 5프레임 연속 판정으로 일시적 분류 변화가 즉시 상태 변경이 되는 것을 억제한다.
- 영상 외에 가속도와 SHOCK 입력을 사용해 관측을 조합한다.

### 한계

- 기둥 하나로 건물 전체 거동을 대표하기 어렵고 기울임만으로 지진 원인을 확정할 수 없다. 카메라 흔들림·충격·조명이 오탐을 만들고, 기울임이 눈에 띄지 않는 진동은 놓칠 수 있다.
- 기둥이 중앙 크롭 안에 들어오도록 설치해야 한다. 카메라·기둥 위치가 바뀌면 학습 조건과 달라질 수 있다.
- `MIN_CONFIDENCE = 0.0`이라 저신뢰 결과를 사실상 거부하지 않는다. 모호한 영상도 같은 클래스가 5번 나오면 확정될 수 있다. 모델 점수를 보정 없이 실제 정답 확률로 해석하지 않는다.
- 5프레임은 시간 기준이 아니므로 부하에 따라 확정 시간이 변한다. 경보 진입과 해제에 같은 연속 판정 조건을 적용한다.
- 각도·변화율·가림 여부와 신뢰도를 서버로 전달하지 않고, 여러 기둥을 개별적으로 구분하지 않는다.

### 개선 제안

1. 고정 ROI와 정상 기준을 확보하고 마커·고정 배경으로 카메라 움직임을 구분한다. 실제 각도가 필요하면 보정과 기준 측정 후 회귀·선분/마커 기반 추정을 비교한다.
2. 저신뢰·가림·카메라 실패를 `UNKNOWN` 등 별도 상태로 전달한다. 검증 데이터로 신뢰도 기준과 경보 진입·해제의 지속 시간을 정한다.
3. 정상 진동·충격·카메라 흔들림·조명 변화 데이터를 추가한다. 촬영 세션별로 학습·평가를 나눠 인접 프레임 유출에 따른 성능 과대평가를 방지한다.
4. 매 프레임 전체 점수 출력, 전처리, 촬영 버퍼의 비용을 측정한다. 최신 프레임 중심의 제한된 큐와 `FRAME_DELAY` 조정을 검토한다.
5. Jetson 기종·JetPack·지원 연산 확인 후 TensorRT와 FP16/INT8 변환을 검토한다. 정확도·지연·메모리를 실제 보드에서 비교하고 효과를 사전에 보장하지 않는다. [NVIDIA TensorRT 문서](https://docs.nvidia.com/deeplearning/tensorrt/latest/)

## 4. 센서·Jetson 통합 방식

센서 경로는 STM32 → ESP Wi-Fi/TCP → 중계 서버 → SQL 클라이언트다. 영상 경로는 카메라 → Keras 실행 클라이언트 → TCP 중계 서버 → SQL 클라이언트다. SQL 클라이언트는 통합 판정 후 서보 명령과 DB 기록을 처리한다.

송신 메시지에는 원본 측정 시각과 장치 순번이 없다. 중계 서버는 앞부분을 송신자 ID로 바꿔 전달한다.

```text
STM32: [PJS_SQL]SENSOR@ax@ay@az@shock\n
Jetson: [PJS_SQL]STATUS@WARNING\n
```

### 점수 판정

| 입력 | 조건 | 점수 |
| --- | --- | --- |
| 영상 | WARNING / CAUTION / SAFETY | 4 / 2 / 0 |
| SHOCK | 값이 1 | 2 |
| 가속도 | `abs(sqrt(ax²+ay²+az²) - 16384)` ≥1500 / ≥1000 / 그 미만 | 4 / 2 / 0 |

총점 6 이상은 WARNING, 3 이상은 CAUTION, 그 미만은 SAFETY다. 입력 점수가 짝수라 실제 CAUTION 점수는 4다. 영상 WARNING만으로는 통합 CAUTION이고, 가속도 WARNING과 SHOCK 감지로 영상 SAFETY에서도 통합 WARNING이 가능하다. 모든 입력이 동시에 경고해야 하는 AND 규칙은 아니다.

가속도는 ±2g 기본 범위와 `16384 raw ≈ 1g`를 가정한다. 펌웨어가 범위를 명시적으로 설정하지 않으므로 실제 설정을 확인해야 한다. SHOCK의 `1 = 감지`도 서버 가정이므로 모듈 극성을 검증한다. 가속도 크기는 정적인 방향 변화의 영향을 줄이지만 방향 정보를 잃고 일부 수평 진동에 둔감할 수 있다. 임계값은 주석에서도 실측 튜닝이 필요하다고 명시한다.

## 5. 지연: 네트워크와 판정 대기

| 요소 | 실제 동작과 의미 |
| --- | --- |
| STM32 1000 ms 주기 | 약 1초마다 가속도를 읽고 SHOCK과 전송. 루프·통신 처리로 실제 간격은 늘어날 수 있음 |
| 주기 변경 근거 | 펌웨어 주석은 100 ms 전송이 제어 수신을 방해해 1초로 설정했다고 설명 |
| ESP 전송 | CIPSEND와 데이터 송신 호출에서 각각 1000 ms timeout 인자를 사용. 항상 1초씩 걸리는 것은 아님 |
| 영상 5프레임 확인 | 상태 변경 전 판정 대기 발생 |
| `FRAME_DELAY = 0.03` | 루프마다 30 ms 추가 대기. 추론·촬영 시간이 더해지므로 33 FPS로 단정 불가 |
| heartbeat 1초 | 영상 안정 조건을 충족할 때 상태 변경 즉시 전송 또는 약 1초마다 재전송 |
| 서보 대기 | WARNING 해제 대기 3초, SAFETY 잠금 복귀 5초, 해제 대기 중 SAFETY 취소 기준 2초 |
| DB 기록 | SAFETY는 3초 간격 또는 상태 변경 시, 그 외에는 통합 처리마다 저장 |

5프레임 확인은 첫 판정부터 확정까지 약 4개 처리 주기가 필요하다. 루프 대기만 약 120 ms이고 촬영·추론 등은 추가된다. 상태 변화가 카메라에 잡히기 전 대기는 별도다. 이는 코드에서 계산한 대기 성분이며 실측 종단 지연이 아니다.

서보의 3초도 “WARNING이 반드시 3초 연속 유지”되는 규칙은 아니다. WARNING 뒤 CAUTION이면 타이머를 유지하고, SAFETY에서는 2초 유지 조건으로 취소한다. 타이머는 새 센서 샘플 또는 바뀐 영상 상태로 통합 처리가 실행될 때 확인한다. 독립적인 주기 타이머가 아니므로 정확히 3초·5초에 동작한다고 보장할 수 없고, 데이터가 끊기면 갱신도 멈출 수 있다.

### 네트워크·처리 경로 문제 후보

- SQL 클라이언트는 개행 기준 누적으로 TCP 분할·병합 수신을 처리한다. 그러나 **중계 서버는 `read()` 결과를 바로 하나의 메시지처럼 파싱**한다. 서버에서 먼저 메시지가 훼손될 수 있어 SQL 측 누적만으로 경로 전체가 안전해지지 않는다.
- 서버와 SQL 송신은 `write()` 한 번으로 끝나고 전체 길이 전송 확인·재시도 처리가 없다. Python의 `sendall()`과 달리 부분 쓰기·오류 대응이 필요하다.
- DB INSERT는 수신 스레드 안의 동기 작업이다. 느린 DB·로그 출력은 다음 메시지 파싱을 지연시킬 수 있다. Bluetooth 전달도 DB 성공 후 수행해 DB 장애가 표시 경로에 영향을 준다.
- TCP 재전송과 혼잡은 지연 원인이 될 수 있으나 실제 발생 여부·시간은 미측정이다. Python은 촬영 실패 시 상태 전송을 진행하지 않고 송신 오류 시 루프를 종료한다.

개선 시 중계 서버에도 개행 프레이밍을 적용하고 송신 완료 확인·재접속 정책을 둔다. DB 기록을 판정 경로에서 분리하되 큐 상한과 누락 기록 정책을 정의한다. 영상 최신성 관리와 파형 기록의 연속성 요구는 각각 고려한다.

## 6. 데이터 시간 불일치

`process_sensor()`와 `process_status()`는 파싱 시 `CLOCK_MONOTONIC` 시각을 기록한다. 이는 **측정 시각이 아닌 SQL 클라이언트 처리 시각**이다. DB 작업 뒤에 밀린 메시지도 처리될 때 새 시각이 붙는다. `latest_sensor.sequence++`는 수신 측 처리 횟수여서 송신 누락·중복을 판별할 수 없다.

현재는 최신 센서값과 최신 영상 상태를 결합하고, 새 센서 또는 영상 상태 변화에 재판정한다. 같은 상태의 영상 heartbeat는 시각을 갱신하지만 그것만으로 재판정하지 않는다. 센서 나이는 3초로 제한하지만 Jetson 나이는 출력만 하고 만료시키지 않는다.

`latest_jetson` 초기값은 `SAFETY`, `valid = 1`이다. “두 데이터가 한 번 이상 들어와야 판단”이라는 주석과 달리 **Jetson을 실제 수신하지 않아도 센서만으로 기본 SAFETY를 사용해 판정**할 수 있다. Jetson이 중단되어도 마지막 상태가 무기한 남는다. 수신 측 주석은 상태 변경 전송으로 설명하지만 현재 Python은 안정 조건 아래 heartbeat도 보내므로 주석과 실제 정책이 다르다.

DB `record_date = NOW()`는 저장 시각이라 원래 촬영·측정 시각을 복원하지 못한다. `gyro_x/y/z`에는 실제 가속도가 들어가고 `motor1~8`은 서보 명령 각도이지 실제 위치 피드백이 아니다.

### 개선 제안

1. 장치·세션 ID, 송신 순번, 원본 측정 시각, 단위·품질을 추가한다. 영상 촬영 시각과 추론 완료 시각을 구분하고 신뢰도도 전송한다.
2. 공통 시간 기준과 잔여 오차를 정의한다. NTP를 후보로 검토하고 더 정밀한 요구에는 지원 하드웨어에 맞춰 PTP·공통 트리거를 평가한다. 장치별 단조 시계 값을 직접 빼지 않는다. [NTP RFC 5905](https://www.rfc-editor.org/info/rfc5905/)
3. 짧은 버퍼에서 측정 시각 기준으로 대응시킨다. 허용 시간 차이를 넘으면 매칭 실패로 처리하고 버퍼 대기는 종단 지연에 포함한다.
4. 영상 미수신·만료를 구분한다. 현재 heartbeat는 판정이 안정되지 않으면 전송되지 않으므로 생존 신호와 유효 판정을 분리한다. 누락을 무조건 SAFETY로 바꾸지 않는다.
5. 수신이 없어도 만료와 제어 대기를 확인하는 주기 작업을 검토한다. 데이터 부족 시 판정·제어 정책을 정의하고 검증한다.

## 7. FIR/IIR 적용 여부와 선택 이유

### 실제 적용 여부

검토한 영상·STM32 센서 취득·SQL 판정 경로에 **소프트웨어 FIR/IIR은 구현되어 있지 않다.** 가속도는 raw XYZ의 크기와 1g 대비 차이로 판정한다. 5프레임 연속 판정과 서버 유지 타이머는 상태 안정화 규칙이며 FIR/IIR 신호 필터는 아니다.

MPU6050 초기화는 전원 관리 레지스터에 0을 써서 깨우는 코드뿐이다. DLPF·샘플링 주기·가속도 범위를 명시적으로 설정하지 않는다. 따라서 소프트웨어 필터 미적용과 센서 내부 필터가 전혀 없다는 주장은 구분한다. 내부 상태는 데이터시트·레지스터·실제 장치로 확인해야 한다.

### 개발자가 제시한 미사용 근거: 작은 이상 변화와 응답성 우선

개발자는 지진 관제 시스템이 작은 이상 변화에도 민감하게 반응해야 한다는 관점에서 FIR/IIR 미사용 이유를 제시했다. 코드·주석에는 당시 선택 이유가 없으므로 아래는 개발자가 이번 검토에서 제시한 설계 근거이며, 필터 비교 실험 결과는 아니다.

> 지진 관제에서는 작은 이상 변화와 짧은 진동을 놓치지 않는 것이 중요하다고 판단했다. 필요한 신호 대역과 필터 설정을 검증하기 전에는 필터가 이상 신호를 감쇠시키거나 판정에 지연을 더할 가능성을 고려해 소프트웨어 FIR/IIR 적용을 보류했다. 우선 원시 데이터와 현재 판정 규칙으로 동작을 확인하고, 이후 같은 데이터로 필터 적용 전후의 미탐·오탐·지연을 비교해 도입 여부를 결정한다.

쉽게 말하면, 짧은 변화가 노이즈처럼 보여도 실제 이상 신호일 수 있어 먼저 그대로 관측하겠다는 선택이다. 특히 평활화 성격의 저역통과 설정은 짧은 피크를 줄일 수 있고, 필터의 주파수 응답과 지연은 종류·계수·샘플링 주기에 따라 달라진다. FIR/IIR이라는 이름 자체가 신호를 무조건 약하게 만든다는 뜻은 아니다. [SciPy 필터 설계](https://docs.scipy.org/doc/scipy/reference/generated/scipy.signal.firwin.html), [군지연 설명](https://docs.scipy.org/doc/scipy/reference/generated/scipy.signal.group_delay.html)

이 선택에는 잡음·일상 충격에 의한 오탐이 늘 수 있다는 비용도 있다. 적절한 필터는 오히려 신호 대 잡음비를 개선해 감지를 도울 수 있으므로 민감한 시스템에서 필터를 항상 배제해야 한다는 결론은 아니다. 센서 내부 DLPF·취득 전 anti-alias 처리와 추가 소프트웨어 필터 도입은 구분해 검토한다.

또한 현재 1초 간격 취득은 짧은 신호를 놓칠 수 있고 연속 판정·제어 유지 시간도 지연을 만든다. 따라서 FIR/IIR 미사용만으로 높은 민감도나 무지연을 보장하지 않는다. 먼저 빠른 취득·구간 계산을 확보한 뒤 필터 후보를 비교한다.

### 필터보다 먼저 해결할 취득 문제

STM32는 약 1초마다 가속도 레지스터와 SHOCK 핀을 한 번 읽는다. 고속 취득한 샘플을 묶어 보내는 구현이 아니므로 사이에 발생한 짧은 충격을 놓칠 수 있다. 센서 내부 샘플링이 빨라도 현재 경로가 전체 파형을 보존하는 것은 아니다.

명목상 1 Hz에서 균일 샘플링을 가정한 나이퀴스트 주파수는 0.5 Hz다. 더 빠른 성분은 적절한 취득 전 필터링 없이 앨리어싱되거나 놓칠 수 있고 서버의 사후 필터로 복원할 수 없다. 100 ms 송신이 수신을 방해했다는 주석을 고려하면 **고속 취득과 네트워크 송신 분리**가 우선이다.

타이머 취득·링버퍼·FIFO 활용 가능성, SHOCK 이벤트 래치를 검토한다. 타임스탬프가 있는 샘플 묶음 또는 구간 RMS·최대값·이벤트 수 전송을 비교하되, 요약값만으로 원본 파형을 복원할 수 없다는 점도 기록한다.

### FIR과 IIR 비교

| 기준 | FIR | IIR |
| --- | --- | --- |
| 구조 | 유한 입력 샘플의 가중합 | 입력과 이전 출력/내부 상태 사용 |
| 장점 | 선형 위상 설계 가능, 유한 계수 비재귀 구조는 안정적 | 유사한 선택도를 낮은 차수로 구현할 수 있어 자원 절약 가능 |
| 주의점 | 탭 수 증가에 따른 연산량·지연 | 주파수별 지연·위상, 수치 안정성 |
| 후보 용도 | 시간 관계 보존이 중요한 파형 분석 | 자원이 제한된 온라인 노이즈 완화 |

선형 위상 FIR의 군지연은 일반적으로 `(N-1)/(2fs)`초다. 향후 100 Hz 취득에서 21탭은 0.1초지만 현재 약 1 Hz 스트림의 같은 탭 수는 약 10초다. 설계 예시이며 실측치가 아니다. IIR도 무지연이 아니고 주파수별 지연이 다를 수 있다. [SciPy firwin](https://docs.scipy.org/doc/scipy/reference/generated/scipy.signal.firwin.html), [SciPy group_delay](https://docs.scipy.org/doc/scipy/reference/generated/scipy.signal.group_delay.html)

### 도입·미적용을 결정할 기준

실제 취득 주기·내부 필터·노이즈·필요 대역을 먼저 확인한다. 느린 기울임 관측과 진동 분석에 다른 필터가 필요할 수 있다. 기울임 경로에서 느린 변화·DC를 제거하면 변형을 놓칠 수 있다. 필터는 네트워크 지연이나 시계 오차를 해결하지 않는다.

필터 없음·짧은 FIR·낮은 차수 IIR을 같은 기록에 적용해 오탐·미탐·진폭 왜곡·판정 지연을 비교한다. 효과가 작거나 추가 지연이 목표를 넘으면 미적용을 유지할 근거가 된다. 노이즈가 판정을 흔들고 유효 신호를 보존하면서 개선되면 도입 근거가 된다. 차단 주파수를 실험 없이 고정하지 않는다.

IIR은 수치 안정성을 위해 SOS 형태를 검토하고 패킷 경계마다 상태를 초기화하지 않는다. 이동평균은 FIR, EMA는 IIR이다. 고정 계수 필터는 균일 샘플 간격을 전제로 설계하므로 원본 측정 시각·결측 처리를 먼저 정의한다. `filtfilt`는 미래 샘플이 필요한 순방향·역방향 처리여서 즉시 온라인 판정에 그대로 적용할 수 없다. [SciPy sosfilt](https://docs.scipy.org/doc/scipy/reference/generated/scipy.signal.sosfilt.html), [SciPy filtfilt](https://docs.scipy.org/doc/scipy/reference/generated/scipy.signal.filtfilt.html)

## 8. 후속 검증 우선순위

| 순서 | 개선 | 확인할 결과 |
| --- | --- | --- |
| 1 | 서버 프레이밍·송신 완료 처리, 영상 미수신·만료 구분 | 분할·병합 처리, 중단 후 오래된 값 사용 여부 |
| 2 | 센서 취득·송신 분리, 측정 시각·순번 | 샘플 간격·누락, 짧은 충격 보존, 제어 수신 지연 |
| 3 | 시간 정렬·DB 경로 분리·주기적 만료 처리 | 시각 차이, 큐 길이, DB 지연 중 판정·제어 |
| 4 | 영상 신뢰도·ROI·지속 시간 | 세션별 재현율·오탐, 촬영부터 확정까지 지연 |
| 5 | 필터·추론 최적화 비교 | 미탐·오탐·지연·자원 사용량 |

정상·기둥 기울임·카메라 흔들림·짧은 충격·단절·느린 DB·TCP 분할/병합을 포함해 실험한다. 서보 명령과 실제 위치를 구분하고, 단계별 시간과 종단 지연 p50/p95/p99를 기록한다. 이번 문서는 정적 검토 결과이며 실제 지진 감지 성능과 네트워크 병목의 빈도, 필터 효과는 실측으로 확인해야 한다.
