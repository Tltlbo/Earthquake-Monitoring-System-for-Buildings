# 현재 환경의 문제 상황과 해결 방안

작성일: 2026-10-11  
검토 기준: `develop` 기반 소스와 개발자가 보고한 현상  
관련 문서: [기술 선택과 전체 구조](troubleshooting-and-technical-decisions.md)

이 문서는 문제 해결을 위한 설계·검증 계획이다. 아래 개선은 아직 코드에 적용하지 않았다. 두 가지 보고된 현상은 관측 사실로 기록하되, 로그 없이 정확한 원인을 확정하지 않는다. 추가 항목은 코드에서 확인한 동작이 만들 수 있는 문제다.

## 1. 1초에 한 번 읽는 센서가 중간의 흔들림을 놓치는 문제

### 무엇이 문제인가?

실제로 센서는 양수와 음수로 흔들렸는데 관제에는 비슷한 값만 들어와 지진 판정이 나오지 않았다는 현상이다. 현재 코드를 보면 우선 의심할 부분은 **1초마다 센서값을 한 번 읽고, 그 값만 전송하는 방식**이다.

[STM32 main.c](../hardware/earthquake_detection/Core/Src/main.c)는 1초가 지났을 때 MPU6050를 읽고 바로 전송한다. 1초 동안의 변화를 모아서 보내는 것이 아니다. 여기서 “캡처”는 이 순간값 읽기를 뜻한다. 별도 캡처 프로그램이 있다면 그 과정도 확인해야 한다.

설명용으로 다음과 같이 흔들렸다고 생각해 보자. 값은 한 축의 정상 기준 대비 변화량이며 실측치가 아니다.

| 시간 | 실제 변화 | 현재 STM32가 읽는 값 |
| --- | --- | --- |
| 0.0초 | 0 | 읽고 전송: 0 |
| 0.2초 | +2000 | 읽지 않음 |
| 0.4초 | -2000 | 읽지 않음 |
| 0.6초 | +2000 | 읽지 않음 |
| 0.8초 | -2000 | 읽지 않음 |
| 1.0초 | 0 | 읽고 전송: 0 |

관제에는 `0 → 0`만 도착한다. 중간에 크게 흔들렸지만 그 순간을 STM32가 읽지 않았으므로 관제에서 알 수 없다. 실제로 항상 이런 패턴이라는 뜻은 아니며, 현재 방식에서 가능한 미탐 사례다.

따라서 1초 전송을 문제로 보는 의견은 현재 구조와 맞닿아 있다. 다만 **빠르게 읽어서 계산한 결과를 1초마다 보내는 것**과 **1초마다 한 번만 읽어서 보내는 것**은 다르다. 전자는 그 사이의 흔들림을 요약할 수 있지만, 현재의 후자는 놓칠 수 있다.

### 왜 STM32에서 먼저 계산하는 해결안인가?

관제에서 필터를 추가하거나 임계값을 낮춰도, STM32가 읽지 않은 중간 값은 되찾을 수 없다. 센서가 있는 STM32에서 먼저 충분히 자주 읽어 변화를 잡아야 한다.

그렇다고 읽을 때마다 전송하면 통신 처리도 늘어난다. 실제 펌웨어 주석에는 100 ms 전송이 제어 명령 수신을 방해해 1초로 바꿨다는 설명이 있다. 그래서 **센서는 빠르게 읽고, 판단에 필요한 계산은 STM32에서 하며, 통신은 필요한 때 수행하는 방식**을 우선 개선안으로 제안한다.

### 제안 구조: 빠른 취득 → 보드 내부 계산 → 이벤트 전송

| 단계 | STM32가 수행할 일 | 이렇게 하는 이유 |
| --- | --- | --- |
| 취득 | 정해진 짧은 간격으로 XYZ를 읽어 버퍼에 보관 | 전송 사이에 생긴 흔들림도 관측 |
| 계산 | 최근 짧은 구간의 최대·최소·흔들림 크기를 계산 | 특정 순간값 하나가 아닌 구간 전체 변화로 판단 |
| 이상 후보 판단 | 기준 초과와 지속 조건을 확인 | 작은 노이즈나 단발 변화로 전송이 반복되는 것을 억제 |
| 전송 | 이상 시작·등급 변화·회복 때 요약 결과 전송 | 모든 샘플 전송에 따른 통신 부하를 줄이면서 상태 변화 전달 |
| 정상 확인 | 별도의 낮은 빈도 heartbeat 전송 | 조용한 정상 상태와 보드·통신 중단을 구분 |

예를 들어 10 ms마다 읽기(100 Hz), 최근 100~200 ms 구간 계산을 초기 실험 후보로 삼을 수 있다. 이는 권장 확정값이 아니다. 필요한 진동 대역, MPU6050 설정, 실제 처리 시간에 맞춰 정해야 한다. 구간이 길수록 정보를 모으기 쉽지만 판정 대기도 길어질 수 있다.

이상 후보가 발생하면 다음 정상 전송 주기를 기다리지 않고 전송 큐에 넣는다. 관제는 STM32의 센서 요약 결과를 영상 상태와 결합해 최종 판정한다. STM32에서 센서 계산을 하더라도 곧바로 서보를 제어하도록 바꾸는 것은 별도 정책 결정이다.

### 구간이란 무엇인가?

구간은 **최근 일정 시간 동안 읽은 센서값 여러 개를 모아 보는 범위**다. 기존에는 지금 값 한 개만 봤다면, 개선안은 최근에 어떤 변화가 있었는지 함께 본다. 센서 취득 주기, 계산 구간, 전송 시점은 서로 다른 설정이다.

예를 들어 10 ms마다 읽고 최근 20개를 계산한다면 약 200 ms를 대표하는 구간이 된다. 20개 샘플의 첫 시각과 마지막 시각 차이는 190 ms이고, 여기서는 20개의 샘플 간격을 기준으로 200 ms 길이라 부른다. 실제 구간 시작·끝 시각과 샘플 수는 메시지에 기록한다. 이 수치는 설명용 초기 후보이며 확정 설정이 아니다.

20개를 확보한 뒤 새 값이 들어올 때마다 가장 오래된 값 하나를 빼고 새 값 하나를 넣는 **이동 구간**을 사용할 수 있다. 그러면 매번 새 200 ms가 끝날 때까지 기다리지 않고 최근 변화를 갱신한다. 계산을 매 샘플마다 할지 몇 샘플마다 할지는 처리 여유에 따라 검증한다. 시작 직후 데이터가 충분하지 않은 상태도 따로 표시한다.

짧은 구간은 빠르게 반응하지만 잡음·단발 충격에도 민감할 수 있다. 긴 구간은 지속되는 흔들림을 보기 좋지만 짧은 피크의 RMS가 작아지고 변화가 오래 남을 수 있다. 따라서 “구간을 정했다” 자체가 해결이 아니라 **놓치는 이벤트와 추가 지연을 비교해 길이를 고르는 과정**이 필요하다.

### 보드 안에서는 무엇을 계산하면 좋은가?

처음에는 복잡한 필터보다 **각 축에서 얼마나 크게 오갔는지**를 계산하는 방법부터 비교한다.

- 최대-최소 차이: 위 예시의 `+2000`과 `-2000`은 차이가 4000이다. 시작과 끝이 0이어도 구간 안에서 흔들렸다는 사실을 남긴다.
- 기준 대비 최대 절댓값: 정상 기준에서 가장 크게 벗어난 정도다. 짧은 큰 변화에 반응하지만 단발 충격에도 민감할 수 있다.
- RMS: 기준 대비 변화의 전반적인 크기를 보는 값이다. 양수·음수를 그대로 평균내면 서로 상쇄될 수 있어, 제곱해 평균낸 뒤 제곱근을 취한다.

단일 지표만으로 지진 원인을 확정하지 않는다. 정상 진동·충격·기울임 실험으로 지표와 임계값을 비교한다. 정상 기준은 중력과 센서 설치 방향을 포함하므로 장치 교정이 필요하고, 자동으로 계속 갱신하면 실제 변화까지 정상으로 흡수할 수 있다.

### RMS는 왜 사용하며 어떻게 계산하는가?

관심 대상은 양수인지 음수인지보다 **그 구간에서 얼마나 크게 움직였는지**다. 예를 들어 한 축의 정상 기준 대비 변화가 `0, +2000, -2000, 0`이면 단순 평균은 0이다. 실제로 움직였지만 양수와 음수가 서로 지워진다.

RMS는 각 값을 제곱한 뒤 평균을 내고 제곱근을 구한다. 따라서 양·음 변화가 상쇄되지 않고, 결과 단위도 입력과 같다. [MathWorks RMS 정의](https://www.mathworks.com/help/matlab/ref/rms.html)

```text
기준 대비 변화:  0, +2000, -2000, 0
단순 평균:       (0 + 2000 - 2000 + 0) / 4 = 0
제곱 평균:       (0 + 4,000,000 + 4,000,000 + 0) / 4 = 2,000,000
RMS:             sqrt(2,000,000) ≈ 1414 raw
최대-최소 차이:  2000 - (-2000) = 4000 raw
```

이는 계산을 설명하기 위한 4개 가상 샘플이며 지진 데이터나 경보 기준이 아니다. 단순 평균 0과 달리 RMS는 구간의 움직임을 남긴다. 다만 RMS는 지속 여부나 지진 원인을 직접 알려주지 않으며 단발 충격도 RMS를 올릴 수 있다. 최대-최소 차이는 가장 큰 폭을, RMS는 구간 전반의 크기를 보므로 함께 비교할 후보로 삼는다. 실제 유용성은 실험으로 확인한다.

각 축에서 `변화 = 측정값 - 정상 기준값`을 계산한 뒤 축별 RMS와 최대-최소 차이를 구한다. 중력을 포함한 raw XYZ의 RMS를 곧바로 진동으로 해석하면 정지 상태에서도 큰 값이 나온다. 기준 교정·자세 변화 대응이 필요하고, 기울임 관측은 별도 경로로 유지한다. XYZ를 한 순간에 제곱해 합치는 기존 방식과 달리 여기서는 **각 축의 여러 시점 변화량**을 평가한다. C 구현에서는 제곱·누적 중 정수 오버플로가 나지 않게 타입과 범위를 정한다.

### 어떤 순서로 접근하고 전송을 결정하는가?

1. **정상 데이터부터 모은다.** 설치 후 정지 상태와 일상 진동에서 기준값, 잡음 범위, 샘플 간격을 측정한다. 정상과 이상 테스트는 분리하고 임계값을 실제 데이터로 정한다.
2. **빠르게 취득한다.** 타이머/data-ready 기준으로 XYZ와 취득 시각을 버퍼에 넣는다. 송신 중에도 취득 간격과 누락을 확인한다.
3. **최근 구간을 계산한다.** 충분한 샘플이 모이면 기준 대비 축별 변화의 RMS와 최대-최소를 계산한다. 누락이 큰 구간은 정상 판정 대신 품질 저하로 표시한다.
4. **센서 이상 후보를 판단한다.** 초기 비교안으로 축별 최대-최소 또는 RMS가 검증한 진입 기준을 넘으면 후보 이벤트를 만든다. “또는” 규칙은 미탐을 줄일 수 있지만 오탐을 늘릴 수 있어 비교 대상이지 확정 규칙이 아니다. 필요하면 연속 구간·최소 지속 시간을 적용하되 그 지연을 기록한다. 겹치는 구간은 독립 관측이 아니므로 두 구간 초과를 곧 두 번의 독립 진동으로 보지 않는다.
5. **변화가 있을 때 보낸다.** 정상에서 후보로 바뀌면 구간 시각·특징값·품질을 송신 큐에 넣는다. 계속 같은 상태면 전송 빈도를 제한하고, 낮은 복귀 기준을 일정 시간 만족하면 회복 이벤트를 보낸다. 정상 때는 생존 신호를 보낸다.
6. **관제가 영상과 결합한다.** 측정 시각을 맞추고 센서 후보와 Jetson 상태를 평가한다. RMS 초과를 곧 지진 확정이나 서보 구동으로 연결하지 않는다.

예를 들어 “센서는 빠르게 읽지만 아무 변화가 없으면 생존 신호만 전송하고, 구간 안에서 변화가 커지면 센서 이상 이벤트를 전송한다”가 핵심 동작이다. 구간 계산과 전송 사이에 대기열이 생길 수 있으므로 ‘이벤트 발생 즉시 큐 등록’과 ‘관제 도착’의 시간을 구분한다.

이 방식도 데이터 여러 개를 묶어 보는 만큼 시간 반응 특성이 있고 RMS가 피크를 희석할 수 있다. FIR/IIR 미적용을 모든 평균·구간 계산 배제로 설명하지 않는다. 원본·피크 정보와 RMS를 함께 평가해 작은 이상 변화 보존이라는 목적에 맞는지 검증한다.

### 추가로 확인해야 할 계산 문제

빠르게 읽더라도 **현재 관제의 계산식을 그대로 쓰는 것만으로 해결되지 않을 수 있다.**

[central_client.c](../SQLClient/central_client.c)는 XYZ를 제곱해 합친 전체 크기를 계산한 뒤 1g 기준과 얼마나 다른지 본다. `+2000`과 `-2000`을 제곱하면 같아지므로 방향 변화는 이 계산에서 사라진다.

예를 들어 `(+2000, 0, 16384)`와 `(-2000, 0, 16384)`는 전체 크기가 같고 1g 기준과의 차이도 약 122 raw로 현재 주의 기준 1000보다 작다. 설명용 예시다. 이것은 센서값의 부호가 통신에서 없어졌다는 뜻이 아니라, **판정 지표가 부호 변화 자체를 보지 않는다는 뜻**이다. 부호를 무시하는 방식이 항상 틀린 것은 아니지만 현재 목적에 맞는지 검증해야 한다.

또한 현재 통합 점수에서 가속도 CAUTION 단독은 최종 SAFETY다. 원본을 잘 읽었는지, 센서 지표가 기준을 넘었는지, 최종 점수가 충분했는지를 각각 기록해야 미탐 위치를 찾을 수 있다.

### 실제 적용 시 함께 바꿀 부분

1. 타이머나 센서 data-ready를 취득 기준으로 삼고, 필요한 MPU6050 샘플링·내부 필터 설정을 확인한다. 인터럽트 안에서는 신호/순번만 남기고 긴 I2C·통신 처리는 실행 구조에 맞게 분리한다.
2. 현재 ESP 송신은 응답을 기다리는 방식이므로 전송 중 센서 취득이 멈추지 않게 상태 머신·DMA·작업 분리 등을 검토한다. 빠른 주기 조건만 추가하면 기존 블로킹 송신 때문에 실제 취득 간격이 다시 벌어질 수 있다.
3. 메시지에 구간 시작·끝 시각, 샘플 수, 순번, 최대-최소 차이/RMS, 센서 상태와 품질을 포함한다. 현재 서버는 raw XYZ를 기대하므로 송신·관제 파서를 함께 변경한다. 요약값을 기존 XYZ 필드에 넣으면 기존 계산이 잘못된다.
4. 같은 이상이 이어질 때는 모든 계산 주기마다 보내지 않고 제한된 주기로 재전송한다. 해제에는 별도 복귀 기준을 두어 상태가 반복해서 바뀌지 않게 한다.
5. 이벤트 전송 실패를 처리하고 상태·순번 기반 중복 처리를 정의한다. heartbeat 만료는 데이터 부족으로 표시한다. 중요한 이벤트 유실 대응은 전송 완료뿐 아니라 관제 수신 확인·제한된 재시도까지 검토한다.
6. 원본 일부를 링버퍼에 남겨 이상 전후 파형을 확인한다. 최대-최소/RMS 같은 요약만 보내면 원래 파형을 복원할 수 없다.

FIR/IIR은 빠른 취득이 확보된 다음 노이즈 완화가 필요한지 비교한다. 다운샘플링에는 적절한 anti-alias 처리가 필요하며, 사후 필터로 이미 놓친 샘플을 복원할 수 없다. [SciPy 다운샘플링 문서](https://docs.scipy.org/doc/scipy/reference/generated/scipy.signal.decimate.html)

### 어떤 실험으로 해결 여부를 확인할까?

- 1초 사이에만 짧게 흔들어 기존 순간값 방식과 보드 내부 구간 계산 방식을 비교한다.
- 시작·끝 값은 같고 중간에 양수·음수로 오가는 입력에서 최대-최소와 RMS가 변하는지 확인한다.
- 통신 전송 중에도 실제 취득 간격과 샘플 수가 유지되는지 측정한다.
- 정상 상태는 낮은 통신량을 유지하고 이상 발생 때는 다음 1초 주기를 기다리지 않는지 확인한다.
- 단발 충격·지속 진동·느린 기울임을 구분해 오탐·미탐과 최초 변화부터 관제 판정까지의 시간을 기록한다.
- 보드 중단·전송 실패·회복 시 관제가 오래된 정상값을 계속 사용하는지 확인한다.

우선 검증할 방향은 **STM32가 빠르게 관측하고 구간의 변화를 계산한 뒤, 이상 이벤트와 회복을 중심으로 전송하며 정상 때는 생존 신호를 보내는 구조**다. 실제 원인이 취득 누락인지 계산식인지 확인할 수 있도록 원본과 중간 결과를 함께 기록한다.

## 2. Teachable Machine 모델이 배경에 따라 흔들림

### 관측 현상과 원인 후보

Teachable Machine으로 학습한 Keras 모델의 감지가 배경에 따라 달라진다. 같은 기둥 상태에서도 배경·조명 조건이 바뀌면 상태가 오락가락한다는 개발자 보고다.

[영상 코드](../detect/detect_earthQuake.py)는 전체 프레임을 중앙 크롭해 224×224로 분류한다. 기둥만 자동으로 분리하지 않으므로 배경도 입력에 포함된다. 학습 시 상태별로 배경·촬영 장소가 달랐다면 모델이 기울임 대신 배경을 단서로 삼았을 가능성이 있다. 이는 학습 데이터 확인과 배경 교체 실험으로 검증해야 한다. Teachable Machine 또는 Keras 자체가 반드시 배경에 약한 것은 아니다.

`MIN_CONFIDENCE = 0.0`으로 저신뢰를 거부하지 않고 5프레임 같은 클래스만 확인한다. 따라서 잘못된 배경 단서가 지속되면 안정적으로 오답을 확정할 수 있다. 연속 판정만 강화해서 배경 의존성을 해결할 수 없다.

### 해결 방안

1. **설치와 입력 영역을 먼저 통제한다.** 카메라를 고정하고 실제 기둥 중심의 ROI를 설정한다. 기둥이 잘리거나 움직여 ROI를 벗어나면 입력 이상으로 처리한다. 재학습 시에도 같은 ROI·224×224·RGB·정규화 과정을 적용한다.
2. **모든 상태에 다양한 배경을 포함한다.** 같은 배경에서 SAFETY·CAUTION·WARNING을 모두 촬영하고 배경·조명·거리 조건을 골고루 분포시킨다. 한 클래스와 특정 장소가 결합되지 않게 한다. 사람이 지나감·그림자·가림·카메라 흔들림도 포함한다.
3. **학습과 평가는 촬영 세션·배경별로 나눈다.** 연속 영상의 이웃 프레임을 무작위로 나누면 실제 일반화보다 높은 점수가 나올 수 있다. 학습에 없던 배경에서 같은 기둥 상태를 유지해 검사한다.
4. **증강은 라벨을 보존하는 범위만 사용한다.** 밝기·대비·작은 위치 변화는 후보지만 기둥 각도가 라벨 기준이라면 회전 증강으로 정답 의미가 바뀔 수 있다. 각도·임계값을 넘어서는 회전을 같은 라벨로 넣지 않는다. [TensorFlow 데이터 증강 문서](https://www.tensorflow.org/tutorials/images/data_augmentation)
5. **불확실한 결과를 별도 처리한다.** 검증 데이터로 최소 점수·클래스 간 점수 차이를 평가하고 `UNKNOWN` 상태를 전송하도록 송수신 규약을 함께 설계한다. 현재 서버는 3개 상태만 허용하므로 송신 측만 추가하면 수신에서 거부된다. 높은 점수도 배경 편향을 배제하지 못한다.
6. **기하학적 비교 기준을 만든다.** 기준 마커·선분 기반 기울기 측정과 모델 결과를 비교한다. 카메라 보정·흔들림 분리도 필요하다. 여러 대상 검출이 필요해지면 경량 검출/추적과 ROI 분류 조합을 평가하되, 즉시 YOLO로 바꾸는 것이 필수 해결책은 아니다.

### 검증 기준

- 동일 기울임에서 배경만 바꾼 테스트의 클래스 전환율과 클래스별 재현율을 비교한다.
- 동일 배경에서 기울임만 바꿔 모델이 실제 상태 변화에 반응하는지 확인한다.
- 기존 전처리와 ROI 재학습 결과를 같은 평가 세트에서 비교하고 오탐·미탐·UNKNOWN 비율·지연을 함께 기록한다.
- 배경을 바꿔도 유지되는 결과와 새로운 기울임에 대한 감도를 모두 확인한다.

## 3. 추가로 확인한 문제와 해결 방향

아래는 실제 장애 발생이 확인된 목록이 아니라 코드에서 확인한 취약한 동작과 재현할 상황이다.

| 문제 상황 | 코드 근거와 영향 | 해결 방향 | 검증 상황 |
| --- | --- | --- | --- |
| Jetson이 한 번도 연결되지 않았는데 SAFETY를 사용 | `latest_jetson` 초기 상태 SAFETY, `valid=1` | 미수신 상태와 실제 정상 판정 분리 | 센서만 연결하고 시작 |
| Jetson 중단 후 예전 상태가 남음 | 영상 age는 출력만 하고 만료시키지 않음 | 생존 heartbeat·판정 유효성 분리, 만료 상태 추가 | 정상/경고 상태에서 각각 Jetson 중단 |
| 다른 시간의 센서·영상을 결합 | 원본 측정 시각 없이 파싱 시각과 최신 값 사용 | 측정 시각·송신 순번과 허용 매칭 간격 추가 | 한 입력만 의도적으로 지연 |
| TCP 데이터가 나뉘거나 합쳐지면 중계가 깨짐 | SQL은 개행 누적하지만 서버는 read 결과를 즉시 파싱 | 서버에도 누적 프레이밍, 길이 제한·잘못된 입력 처리 | 메시지 분할·여러 줄 일괄 송신 |
| 메시지가 일부만 전송되거나 송신 오류를 놓침 | 서버·SQL의 단일 write, 완료 확인 없음 | 전체 길이 송신 루프·오류·재접속 처리 | 송신 부하·연결 해제 |
| DB가 느려 판정 입력 처리가 밀림 | 수신 스레드의 동기 INSERT, Bluetooth는 DB 성공 후 전달 | 판정·기록·표시 경로 분리와 큐 상한 | 느린/중단 DB에서 판정 지연 측정 |
| 짧은 SHOCK 이벤트 누락 | 약 1초마다 GPIO 순간 읽기 | 극성 검증 후 인터럽트/이벤트 래치·카운터 | 읽기 사이의 짧은 펄스 |
| 설정·단위가 맞지 않아 가속도 점수 오판 | ±2g·16384 기준 가정, 범위 명시 설정 없음 | 범위·내부 필터 설정 명시/읽기, 단위 변환·교정 | 정지·알려진 방향·기준 입력 |
| 서보 타이머가 통신 입력에 종속 | 통합 처리 때만 확인, WARNING 뒤 CAUTION에도 대기 유지 | 주기적 시간 검사와 전이 정책 명시 | WARNING→CAUTION, WARNING 후 데이터 단절 |
| 관제 상태를 실제 지진/서보 위치로 오해 | 점수 규칙, DB motor는 명령값이며 gyro는 가속도 | 판정 정의·단위·컬럼 의미 명시, 필요 시 피드백 추가 | 명령은 전송됐지만 구동 실패한 경우 |

한 기둥의 기울임 이상과 센서 점수만으로 지진의 원인을 확정하기 어렵다는 범위 한계도 있다. 현재 검증에서는 “이상 관측 감지”와 “지진 여부 판별”을 구분하고, 향후 여러 기둥·층과 기준 센서 실험으로 확장한다.

## 4. 실행 순서와 완료 판단

1. 원본 signed XYZ부터 최종 점수까지 같은 실험의 로그를 확보해 가속도 미탐 위치를 찾는다.
2. 센서 취득·송신 분리와 구간 특징을 검증하고, 동시에 고정 ROI·배경 균형 데이터로 모델을 재평가한다.
3. 미수신·만료 상태와 측정 시각을 도입하고 TCP 중계의 메시지 경계를 보완한다.
4. DB 처리와 제어 타이머를 정리한 후 정상·충격·흔들림·단절 실험으로 전체 경로를 평가한다.

허용 오탐·미탐·최대 지연은 요구사항으로 정한 뒤 판단한다. 실제 측정 결과가 없는 현재 시점에는 해결 완료나 특정 개선율을 주장하지 않는다. 장치에 적용할 때는 이상 판정과 서보 제어 정책을 함께 검증한다.
